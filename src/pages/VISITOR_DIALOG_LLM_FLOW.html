Visitor Dialog — STT → LLM → Sistem Tepkisi Akışı

Bu döküman tek bir soruya odaklanır:

Bir STT çıktısı geldiğinde, LLM'e ulaşana kadar hangi filtrelerden
geçer; PromptBuilder hangi koşula göre hangi prompt'u inşa eder; hangi
durumda farklı bir agent kontrolü devreye girer; LLM hangi girdiye
hangi response'u döner; sistem bu response'a nasıl tepki verir?

Diğer akışlar (oturum açılışı, timer expired, validation arka plan task'ı,
terminal state aksiyonları) bu dökümanın kapsamı dışındadır — onlar
için bkz. VISITOR_DIALOG_FLOW.md.

1) STT → LLM Arası Filtreler (Uçtan Uca Tek Bakış)

Adım Konum Geçemezse
F1. ctx kuruldu mu, FSM terminal değil mi _on_stt_transcript ilk satırlar drop
F2. state VALIDATING değil mi aynı handler drop (V5 notu: ileride buffer'lanabilir)
F3. text.strip() boş değil mi aynı handler drop
F4. silence timer iptal + count=0 yan etki —
F5 (sadece ON_HOLD'da). _has_resume_signal regex deterministik, ücretsiz drop + on_hold_timer rearm; history'e yazılmaz
F6 (sadece ON_HOLD'da). HoldClassifier.classify (ayrı LLM, PROMPT-C) LLM çağrısı, temp=0, max_tokens=50 drop + on_hold_timer rearm; history'e yazılmaz
F7. ctx.history.append({user, text}) kümülatif —
F8. PromptBuilder.build_system_prompt(ctx) (PROMPT-A) dinamik —
F9. Ana Dialog LLM chat.completions.create response_format=json_object LLMError → ON_HOLD çıkışındaysa retry, değilse FSM ERROR → FAILED
F10. EntityExtractor.extract(raw) JSON parse ExtractionError → aynı: F9'la aynı dallanma

2) Farklı Agent Kontrolü Hangi Koşulda Devreye Girer?

Yalnızca state == ON_HOLD iken ve F5 (deterministik resume sinyali) geçtikten sonra:

state == ON_HOLD
  AND text içinde digit VEYA resume keyword (tamam/devam/hazırım/
      geldim/geldik/bitti/oldu/tamamdır/blok/daire/numara/kat) var
        ↓
  HoldClassifier.classify(text)  ← AYRI LLM (PROMPT-C, sabit, temp=0)
        ↓
  directed_at_agent ?
    true  → ON_HOLD'dan çık (FSM SPEECH_RECEIVED → _previous_state)
            sonra ana LLM çağrılır (PROMPT-A ile)
    false → ON_HOLD'da kal, history'e yazma, on_hold_timer rearm

ON_HOLD dışındaki hiçbir state'te HoldClassifier devreye girmez — STT
transcript doğrudan ana LLM hattına akar.

3) PromptBuilder Hangi Koşullarda Hangi Prompt'u Üretir?

PROMPT-A 5 parça birleşmiş bir string'tir. Sırayla:

[BASE]  +  [STATE-bloğu]  +  [ENTITY HINT]  +  '\n\n'  +  [OUTPUT FORMAT]

[BASE] koşulsuz, her çağrıda aynı.

[STATE-bloğu] ctx.flow_state ve ctx.entities'e göre dallanır:

ctx.flow_state Ek koşul Eklenen blok
GREETING veya COLLECTING_INFO block boş VEYA apartment boş "Şu an şu bilgileri toplaman gerekiyor: <eksik olanların listesi>" (eksik olan alanlar dinamik dökülür)
GREETING veya COLLECTING_INFO her ikisi de dolu "Tüm bilgiler toplandı. Şimdi yapman gereken tek şey bilgileri kullanıcıya özetleyip doğruluğunu sormaktır. Giriş izni verme."
CONFIRMING — "Ziyaretçi {block} Blok {apartment}. daireye gitmek istiyor. Bilgileri doğru anlayıp anlamadığını sor."
VALIDATING — "Adres sisteme doğrulanıyor. Kullanıcıyı beklemesi için bilgilendir." (pratikte tetiklenmez — VALIDATING'de transcript drop edilir)
diğer — boş string

[ENTITY HINT] koşullu:

Koşul Eklenen
block dolu VE apartment dolu "Toplanan bilgiler: blok=X, daire=Y."
sadece block dolu "Toplanan bilgiler: blok=X."
sadece apartment dolu "Toplanan bilgiler: daire=Y."
ikisi de boş boş string

[OUTPUT FORMAT] koşulsuz, her çağrıda aynı: kesin JSON şeması +
sinyallerin ne zaman true yapılacağı kuralları.

Silence retry override (inject_directive) — bu döküman kapsamı
dışı; bkz. VISITOR_DIALOG_FLOW.md.

4) Hangi Girdi → Hangi LLM Response → Hangi Reaksiyon

4.1. Ana Dialog LLM (PROMPT-A) Cevap Şeması 

{
  "block":               "<string|null>",   // örn "A", "B", "12"
  "apartment":           "<string|null>",   // örn "5", "12" (pozitif tam sayı string)
  "hold_detected":       <bool>,            // "bekle/dur/bir dakika/wait"
  "should_grant_access": <bool>,            // SADECE açık onay (proaktif yasak)
  "should_reset_session":<bool>,            // "hayır/yanlış/iptal"
  "reply":               "<string>"         // TTS edilecek kullanıcıya yanıt
}

GREETING, ctx boş "B blok" block:"B", apartment:null, reply:"B Blok hangi dairesine?" ENTITIES_PARTIAL COLLECTING_INFO dialog.reply LLM reply
COLLECTING_INFO, block="B" "5. daire" block:null, apartment:"5", reply:"B Blok 5. daire, doğru mu?" ENTITIES_COMPLETE (apply sonrası kümülatif tam) CONFIRMING dialog.reply LLM reply
COLLECTING_INFO, block="A" "daire 0" block:null, apartment:"0" validate_format False (apartment ≥ 1 değil) → ENTITIES_PARTIAL COLLECTING_INFO dialog.reply LLM reply
herhangi (ON_HOLD dışı) "Bir dakika" hold_detected:true, reply:"Tabii, sizi bekliyorum." INTENT_HOLD ON_HOLD silence timer iptal + on_hold_timer start + statik on_hold_msg (LLM reply yok sayılır)
CONFIRMING, ctx tam "evet" / "doğru" / "tamam" should_grant_access:true, reply:"Anlaşıldı." INTENT_CONFIRM VALIDATING silence timer iptal + statik awaiting_resident_msg + arka plan validate task
CONFIRMING, ctx tam "hayır" should_reset_session:true, block:null, apartment:null, reply:"Özür dilerim, bilgileri tekrar alabilir miyim?" reset_entities → INTENT_CANCEL COLLECTING_INFO (pure cancel) dialog.reply LLM reply
CONFIRMING, ctx tam ("A","5") "Hayır A blok değil C blok" block:"C", apartment:null, should_reset_session:true, reply:"C Blok hangi daire?" block dolu → reset_entities ÇALIŞMAZ; apply ile block="C", apartment kümülatif "5" → tam + format ok → ENTITIES_COMPLETE (yeni adres) CONFIRMING (yeni özet+sor) dialog.reply LLM reply
CONFIRMING, ctx tam "Hmm" / belirsiz tüm sinyaller false, block=null, apartment=null, reply:"{block} Blok {apt}. daireye gitmek istiyorsunuz, doğru mu?" yeni alan yok + ctx tam → ENTITIES_COMPLETE (re-ask) CONFIRMING (self-loop) dialog.reply LLM reply
ON_HOLD, prev=COLLECTING_INFO "tamam hazırım" (önce HoldClassifier true) sonra ana LLM: reply:"Hangi blok ve dairedesiniz?" (FSM önce SPEECH_RECEIVED → COLLECTING_INFO) sonra ENTITIES_PARTIAL (ctx hâlâ eksik) COLLECTING_INFO dialog.reply LLM reply

5) Önemli Davranışsal Notlar

  • should_grant_access proaktif yapılamaz. PROMPT-A output kuralında
    açıkça "bilgi tamamlanınca proaktif true yapma; kullanıcının onayını
    bekle" der. Bu yüzden is_complete=True ile should_grant_access=True
    aynı turda gelmez; iki ayrı tur yaşanır (CONFIRMING'e geç → kullanıcı
    "evet" der → VALIDATING'e geç).
  • Pure cancel ≠ düzeltme. CONFIRMING'de should_reset_session=True
    geldiğinde reset_entities yalnızca block ve apartment ikisi de null
    ise     çalışır. Eğer kullanıcı yeni bir block veya apartment söyledi ise
    reset olmaz, apply çalışır → bu "düzeltme" yoluna düşer.
  • ON_HOLD'da history'e yazma kuralı. F5 veya F6 elerse ctx.history
    kirletilmez. Bu sayede ON_HOLD sırasında geçen TV/telefon konuşması
    ana LLM'in bağlamına sızmaz.
  • ON_HOLD çıkışında LLM hatası FAILED yapmaz. ON_HOLD'dan çıkıp ana
    LLM çağrılır ve hata olursa history.pop + FSM INTENT_HOLD ile
    ON_HOLD'a geri dönülür; ziyaretçi tekrar konuştuğunda yeniden denenir.
  • VALIDATING'de transcript yok sayılır. F2 nedeniyle bu state'te
    hiçbir LLM çağrısı tetiklenmez; bu yüzden PROMPT-A'nın VALIDATING
    state-bloğu pratikte boş yere durur (kod yine de tanımlar).
  • ON_HOLD / VALIDATING girişinde LLM reply kullanılmaz. State entry
    bu iki durumda statik mesaj yayımlar (on_hold_msg /
    awaiting_resident_msg). LLM'in ürettiği reply alanı çöpe gider.
    Kullanıcıya konuşulan tek kanal olan dialog.reply topic'i bu
    durumlarda LLM tarafından değil, sabit metin tarafından beslenir.
